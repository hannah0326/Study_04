# PRD 2단계 — 재료 기반 레시피 생성

> 전체 흐름: [1단계 식재료 인식](PRD_step1.md) → **2단계 레시피 생성** → [3단계 프로필·레시피 저장](PRD_step3.md)

## 1. 목적

1단계에서 확정된 식재료 목록(과 사용자의 선택 조건)을 텍스트 모델에 전달해, 지금 있는 재료로 만들 수 있는 레시피를 추천받는다.

## 2. 범위

**포함**
- 확정된 식재료 목록을 입력으로 한 레시피 생성
- 선택 조건 입력(인원수, 조리 시간, 식단 제한 등)
- 레시피 목록·상세 화면
- 부족한 재료 표시, 다시 생성
- 429 등 모델 실패 시 재시도와 대체 모델 전환, 진행 단계 표시

**제외**
- 레시피 저장·프로필·로그인(3단계)
- 이미지 생성, 영양소 정밀 계산, 장보기 연동

## 3. 사용자 스토리

1. 사용자로서 인식된 재료로 만들 수 있는 요리를 추천받고 싶다.
2. 사용자로서 인원수, 조리 시간, 못 먹는 재료 같은 조건을 지정하고 싶다.
3. 사용자로서 마음에 들지 않으면 다시 생성하고 싶다.
4. 사용자로서 추가로 사야 할 재료가 무엇인지 알고 싶다.

## 4. 기술 구성

| 항목 | 결정 |
|---|---|
| 앱 | Python + Streamlit (1단계와 같은 앱, 별도 서버·HTTP API 없음) |
| 배포 | Streamlit Community Cloud (무료) |
| 모델 | `nvidia/nemotron-3.5-lightning:free` (텍스트 전용) |
| 호출 | OpenRouter chat completions, Streamlit 코드(서버)에서만 호출 |
| 입력 | 1단계의 확정 목록(`st.session_state["confirmed"]`) + 사용자 조건 |
| 출력 | 구조화된 JSON 레시피 목록 |

**API 키 보안 원칙** — 1단계와 같다. 키는 `st.secrets` → 환경변수 → `.env` 순으로 읽고, 화면·로그·오류 문구에 출력하지 않는다. Streamlit 코드는 서버에서만 실행되므로 키가 브라우저로 내려가지 않는다.

## 5. 기능 요구사항

### 5.1 입력 조건
| 항목 | 기본값 | 비고 |
|---|---|---|
| 인원수 | 2 | 1–10 |
| 최대 조리 시간(분) | 제한 없음 | 15 / 30 / 60 선택 |
| 식단 제한·알레르기 | 없음 | 자유 입력 또는 선택(예: 채식, 견과류 알레르기) |
| 추가 재료 사용 허용 | 소량(기본 양념류만) | 허용 / 소량 / 불가 |
| 추천 개수 | 3 | 1–5 |

3단계 이후에는 로그인한 사용자의 프로필에 저장된 식단 제한·알레르기·인원수를 기본값으로 채운다.

### 5.2 레시피 생성
- 앱은 재료 목록과 조건을 프롬프트에 넣고, 아래 JSON 형식으로만 답하게 한다.

```json
{
  "recipes": [
    {
      "title": "달걀 채소 볶음밥",
      "summary": "한 줄 설명",
      "servings": 2,
      "time_minutes": 20,
      "difficulty": "easy",
      "ingredients": [
        { "name": "달걀", "amount": "2개", "have": true }
      ],
      "missing": ["참기름"],
      "steps": ["팬을 달군다.", "..."]
    }
  ]
}
```

- `have`는 사용자가 가진 재료인지 여부다. `missing`은 가진 목록에 없는 재료다.
- 레시피는 **한국어로만** 작성하게 한다. (프롬프트에 명시. 모델이 영어로 답하는 경우가 있다)
- 앱은 응답을 검증한다. 필수 필드 누락, `servings`·`time_minutes` 타입 오류, 빈 `steps`는 불량으로 보고 1회 재요청한다. `choices`가 비었거나 `content`가 null인 응답도 같은 불량으로 처리한다.
- 알레르기·식단 제한에 걸리는 재료가 레시피에 들어 있으면 앱이 해당 레시피를 제외한다. (모델 답변만 믿지 않는다)
- `have: true`로 표시된 재료가 실제로 입력 목록에 없으면 앱이 `have`를 `false`로 바로잡고 `missing`에 옮긴다.

### 5.3 화면
- 1단계의 확정 목록 아래(또는 다음 단계 영역)에서 조건을 고르고 "레시피 생성" 버튼을 누른다.
- 진행 단계(요청 → 재시도 → 대체 모델 전환 → 완료)를 1단계와 같은 방식으로 보여 주고, 끝난 뒤에도 "진행 기록"으로 볼 수 있다.
- 레시피 카드 목록(제목, 시간, 난이도, 부족한 재료 수)과 상세 화면(재료, 단계). 부족한 재료는 눈에 띄게 표시한다.
- "다시 생성" 버튼은 같은 입력으로 새 결과를 요청한다.
- **실패는 숨기지 않는다.** 생성이 실패하면 이전에 성공한 결과를 화면에 남기지 않고, 실패했다고 분명히 표시한다. (이전 결과가 이번 결과처럼 보이는 것을 막기 위함)
- 3단계가 붙으면 상세 화면에 "저장" 버튼이 들어간다. (이 단계에서는 자리만 확보)

### 5.4 모듈 구성

Streamlit 앱에는 별도 HTTP 엔드포인트가 없으므로, 로직을 화면과 분리한 모듈 함수로 둔다.

| 위치 | 설명 |
|---|---|
| `src/recipe.py` `generate_recipes(ingredients, options, api_key, on_event)` | 재료·조건 → 레시피 목록. 프롬프트 작성, 호출, 재시도·대체 모델, 파싱·검증, 알레르기 필터 포함 |
| `src/app.py` | 조건 입력, 진행 표시, 레시피 카드·상세 |

호출·재시도·대체 모델 전환의 공통 부분은 1단계의 `recognizer.py`와 중복하지 않도록 공용 모듈로 뽑는 것을 검토한다.

## 6. 모델 호출 시 유의점

- 출력이 길어지므로 `max_tokens`는 2000 이상으로 넉넉히 잡는다. 추론 토큰이 포함될 수 있다.
- **429·5xx:** 2초 뒤 한 번만 다시 시도하고, 그래도 실패하면 대체 모델을 차례로 시도한다. 모델이 없거나(404) 사용 불가(403·410)여도 다음 모델로 넘어간다. 401(키 문제)은 넘어가지 않는다.
- **대체 모델 목록:** 무료 텍스트 모델 중 실제로 응답하는 것만 쓴다. 구현 시 `/api/v1/models`에서 `:free`이면서 텍스트 출력이 되는 모델을 조사하고, 실제 호출로 성공 여부를 확인해 순서를 정한다. 일부 무료 모델은 특정 환경에서만 호출되어 403이 날 수 있다.
- **하루 한도:** 무료 모델은 계정당 호출 횟수에 하루 한도가 있다(크레딧 10달러 미만 계정은 하루 50회, 분당 20회, UTC 기준 초기화). 429가 일시 혼잡인지 한도 소진인지 응답 헤더로 구분해 안내 문구를 다르게 한다. 한도 소진이면 "잠시 후 다시"가 틀린 안내이므로 초기화 시각(한국 시각)을 알려 준다.
- 이 모델의 한국어 품질은 사전 테스트(간단한 질의응답)로만 확인했다. 레시피 품질은 구현 시 샘플 10건으로 직접 평가한다.
- 프롬프트에는 "입력 재료에 없는 재료는 `have: false`로 표시", "안전하지 않은 조리법(익히지 않은 닭고기 등) 금지"를 명시한다.

## 7. 비기능 요구사항

- **성능:** 정상 응답 기준 레시피 3개 생성은 30초 이내를 목표로 한다. 무료 모델이라 보장하지 않는다.
- **안전:** 재료 목록, 조건 입력은 길이를 제한(예: 재료 50개, 항목당 30자)하고 프롬프트에 넣을 때 사용자 입력을 지시문과 구분해서 전달한다. 사용자 입력 속 지시문이 모델 동작을 바꾸지 못하게 한다.
- **남용 방지:** 세션당 분당 요청 수를 제한한다. 방문자 IP를 안정적으로 얻기 어려워 IP 대신 세션 기준이며 완전한 방어는 아니다.
- **고지:** 알레르기 정보는 모델이 틀릴 수 있으므로 화면에 "알레르기는 직접 확인하세요"를 항상 표시한다.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 재료 목록이 비어 있음 | 요청 거부, 1단계로 돌아가도록 안내 |
| 모델 응답 파싱 실패(빈 `choices` 포함) | 1회 재요청 후 실패하면 실패했다고 표시 |
| 제한 조건 때문에 남은 레시피가 0개 | 조건을 완화하도록 안내 |
| 429 / 타임아웃 | 재시도, 대체 모델 전환 후에도 실패하면 안내. 하루 한도 소진이면 초기화 시각 안내 |

## 9. 수용 기준

- [ ] 1단계에서 확정한 재료로 레시피 3개가 생성된다.
- [ ] 각 레시피에 재료, 조리 단계, 시간, 부족한 재료가 표시된다.
- [ ] 레시피가 한국어로 나온다.
- [ ] 알레르기로 지정한 재료가 포함된 레시피는 결과에 나오지 않는다.
- [ ] 보유하지 않은 재료가 `have: true`로 표시되지 않는다.
- [ ] 응답이 깨졌을 때 앱이 죽지 않고, 이전 결과가 남지 않은 채 실패했다고 표시된다.
- [ ] 429 상황에서 재시도와 대체 모델 전환이 진행 화면에 보인다.
- [ ] 브라우저에서 API 키가 보이지 않는다.

## 10. 미결 사항

- 레시피 품질 평가 기준(예: 조리 가능성, 재료 일치율)을 누가 어떻게 볼 것인가?
- 계량 단위(g, 컵, 큰술)를 표준화할 것인가?
- "다시 생성" 시 이전에 나온 레시피를 제외하는 기능이 필요한가?
- 화면 흐름: 단계 사이를 화면 전환 없이 한 화면에서 결과를 확인하게 할지, 마법사처럼 단계를 나눌지(직접 써 보고 정한다).
