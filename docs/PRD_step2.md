# PRD 2단계 — 재료 기반 레시피 생성

> 전체 흐름: [1단계 식재료 인식](PRD_step1.md) → **2단계 레시피 생성** → [3단계 프로필·레시피 저장](PRD_step3.md)

## 1. 목적

1단계에서 확정된 식재료 목록(과 사용자의 선택 조건)을 텍스트 모델에 전달해, 지금 있는 재료로 만들 수 있는 레시피를 추천받는다.

## 2. 범위

**포함**
- 확정된 식재료 목록을 입력으로 한 레시피 생성
- 선택 조건 입력(인원수, 조리 시간, 식단 제한 등)
- 레시피 목록·상세 화면
- 부족한 재료 표시, 다시 생성
- 429 등 모델 실패 시 재시도와 대체 모델 전환, 진행 단계 표시

**제외**
- 레시피 저장·프로필·로그인(3단계)
- 이미지 생성, 영양소 정밀 계산, 장보기 연동

## 3. 사용자 스토리

1. 사용자로서 인식된 재료로 만들 수 있는 요리를 추천받고 싶다.
2. 사용자로서 인원수, 조리 시간, 못 먹는 재료 같은 조건을 지정하고 싶다.
3. 사용자로서 마음에 들지 않으면 다시 생성하고 싶다.
4. 사용자로서 추가로 사야 할 재료가 무엇인지 알고 싶다.

## 4. 기술 구성

| 항목 | 결정 |
|---|---|
| 앱 | Python + Streamlit (1단계와 같은 앱, 별도 서버·HTTP API 없음) |
| 배포 | Streamlit Community Cloud (무료) |
| 기본 모델 | `nvidia/nemotron-3-ultra-550b-a55b:free` (550B, 활성 55B. 안정성을 우선해 사용자가 정함) |
| 대체 모델 | `nvidia/nemotron-3.5-lightning:free`(30B, 활성 3B, 빠르지만 불안정) → `nvidia/nemotron-3.5-super-vl:free` → `poolside/laguna-s-2.1:free` |
| 추론 | 끈다(`reasoning: {"enabled": false}`). 켜면 응답이 길어져 66초 이상 걸리고 토큰을 다 써서 잘린다 |
| 호출 | OpenRouter chat completions, Streamlit 코드(서버)에서만 호출 |
| 입력 | 1단계의 확정 목록(`st.session_state["confirmed"]`) + 사용자 조건 |
| 출력 | 구조화된 JSON 레시피 목록 |

**API 키 보안 원칙** — 1단계와 같다. 키는 `st.secrets` → 환경변수 → `.env` 순으로 읽고, 화면·로그·오류 문구에 출력하지 않는다. Streamlit 코드는 서버에서만 실행되므로 키가 브라우저로 내려가지 않는다.

## 5. 기능 요구사항

### 5.1 입력 조건
| 항목 | 기본값 | 비고 |
|---|---|---|
| 요리 종류 | 제한 없음 | 한식 / 양식 / 중식 / 일식 |
| 난이도 | 제한 없음 | 초급 / 중급 / 고급 (내부 값은 easy / medium / hard) |
| 조리 시간 | 제한 없음 | 15분 이내 / 30분 이내 / 30분 이상 (이내는 최대 시간, **이상은 최소 시간**). 60분 이내는 두지 않는다 |
| 인원수 | 2 | 1–10 |
| 식단 제한·알레르기 | 없음 | 자유 입력 또는 선택(예: 채식, 견과류 알레르기) |
| 추가 재료 사용 허용 | 소량(기본 양념류만) | 허용 / 소량 / 불가 |
| 추천 개수 | 3 | 1–5 |

3단계 이후에는 로그인한 사용자의 프로필에 저장된 식단 제한·알레르기·인원수를 기본값으로 채운다.

### 5.2 레시피 생성
- 앱은 재료 목록과 조건을 프롬프트에 넣고, 아래 JSON 형식으로만 답하게 한다.

```json
{
  "recipes": [
    {
      "title": "달걀 채소 볶음밥",
      "summary": "한 줄 설명",
      "cuisine": "한식",
      "servings": 2,
      "time_minutes": 20,
      "difficulty": "easy",
      "ingredients": [
        { "name": "달걀", "amount": "2개", "have": true }
      ],
      "missing": ["참기름"],
      "steps": ["팬을 달군다.", "..."]
    }
  ]
}
```

- `have`는 사용자가 가진 재료인지 여부다. `missing`은 가진 목록에 없는 재료다.
- 레시피는 **한국어로만** 작성하게 한다. (프롬프트에 명시. 모델이 영어로 답하는 경우가 있다)
- **요리 종류·난이도·조리 시간 조건도 모델에게 요청하는 데서 끝내지 않고 앱이 다시 확인한다.** 모델은 레시피마다 `cuisine`(한식·양식·중식·일식)을 적는다. 영어나 비슷한 말(Korean, 한국요리 등)은 한식·양식·중식·일식으로 맞춘다.
  - 요리 종류: 선택했는데 모델이 밝힌 `cuisine`이 다르면 제외한다. **모델이 `cuisine`을 밝히지 않았거나 알 수 없는 값이면 확인할 수 없어 통과시킨다**(알려진 한계).
  - 난이도: 선택한 난이도와 같은 레시피만 통과한다. (모델이 "쉬움·보통·어려움"으로 답해도 초급·중급·고급으로 맞춘다)
  - 조리 시간: "이내"는 `time_minutes`가 최대 시간을 넘으면, "이상"은 최소 시간(30분) 미만이면 제외한다. 30분 정확히는 "30분 이상"에 포함된다.
  - 제외된 레시피와 이유는 "제외한 레시피"로 보여 주고, 개수가 모자라면 모자란 만큼 다시 요청한다. 조건이 까다로울수록(예: 한식+초급+30분 이상) 제외가 늘어 호출이 늘 수 있다.
- 앱은 응답을 검증한다. 필수 필드 누락, `servings`·`time_minutes` 타입 오류, 빈 `steps`는 불량으로 보고 1회 재요청한다. `choices`가 비었거나 `content`가 null인 응답도 같은 불량으로 처리한다.
- 알레르기·식단 제한에 걸리는 재료가 레시피에 들어 있으면 앱이 해당 레시피를 제외한다. (모델 답변만 믿지 않는다)
- `have`와 `missing`은 모델이 준 값을 쓰지 않고 앱이 다시 계산한다. 이름은 괄호 설명·손질 표현(다진, 삶은 등)·동의어(계란=달걀)를 정리한 뒤, 같거나 한쪽이 다른 쪽의 끝부분일 때(청양고추↔고추) 같은 재료로 본다. 고추↔고추장은 다른 재료다.
- **제목에 있는 재료가 재료 목록에 없는 레시피는 제외한다.** 실제 시험에서 모델이 제목에 없는 재료(고구마, 김치)를 지어낸 적이 있다. 제목에 흔한 식재료 약 50종 중 하나가 있으면 재료 목록에도 있어야 한다.
- **알레르기·식단 제한:** "견과류", "우유", "갑각류" 같은 분류 이름을 넓혀서 파생 식품(아몬드, 버터, 새우젓 등)까지 걸러 낸다. 한 글자 용어(게, 굴)는 이름이 그것과 같을 때만 걸려서 다른 단어 속에서 오작동하지 않는다. 사전에 없는 항목(예: 복숭아)은 입력한 말 그대로 걸러 낸다.
- **추가 재료 정책:** 불가=부족한 재료가 하나라도 있으면 제외, 소량=부족한 재료가 모두 기본 양념류(소금, 간장, 식용유 등)여야 통과, 허용=제한 없음.
- **조건에 맞는 개수가 모자라면** 모자란 만큼 한 번 더 요청한다(최대 2회 요청, 이미 받은 제목은 제외하라고 알린다). 두 번째 요청이 막히면 이미 받은 것만 보여 준다. 걸러진 레시피와 이유는 화면에 "제외한 레시피"로 보여 준다.
- 모델이 형식을 어기면 같은 모델에 1회 다시 요청하고, 그래도 어기면 대체 모델로 넘어간다. (1단계와 달리 형식 오류도 대체 모델 전환 사유다. 기본 모델이 형식을 자주 어겼기 때문이다)

### 5.3 화면
- 1단계의 확정 목록 아래(또는 다음 단계 영역)에서 조건을 고르고 "레시피 생성" 버튼을 누른다.
- 진행 단계(요청 → 재시도 → 대체 모델 전환 → 완료)를 1단계와 같은 방식으로 보여 주고, 끝난 뒤에도 "진행 기록"으로 볼 수 있다.
- 레시피 카드 목록(제목, 시간, 난이도, 부족한 재료 수)과 상세 화면(재료, 단계). 부족한 재료는 눈에 띄게 표시한다.
- "다시 생성" 버튼은 같은 입력으로 새 결과를 요청한다.
- **실패는 숨기지 않는다.** 생성이 실패하면 이전에 성공한 결과를 화면에 남기지 않고, 실패했다고 분명히 표시한다. (이전 결과가 이번 결과처럼 보이는 것을 막기 위함) 실패 메시지는 다음 시도를 누를 때까지 남고(다른 조작으로 화면이 다시 그려져도 사라지지 않는다), 세션 요청 제한과 예상하지 못한 오류도 같은 방식으로 표시한다. 자세한 규칙은 PRD 1단계 6장.
- 3단계가 붙으면 상세 화면에 "저장" 버튼이 들어간다. (이 단계에서는 자리만 확보)

### 5.4 모듈 구성

Streamlit 앱에는 별도 HTTP 엔드포인트가 없으므로, 로직을 화면과 분리한 모듈 함수로 둔다.

| 위치 | 설명 |
|---|---|
| `src/recipe.py` `generate_recipes(ingredients, options, api_key, on_event)` | 재료·조건 → 레시피 목록. 프롬프트 작성, 호출, 재시도·대체 모델, 파싱·검증, 알레르기 필터 포함 |
| `src/app.py` | 조건 입력, 진행 표시, 레시피 카드·상세 |

호출·재시도·대체 모델 전환의 공통 부분은 `src/llm.py`로 분리했다(구현됨). `recognizer.py`와 `recipe.py`가 함께 쓰며, 오류 클래스(`ServiceError`, `RateLimitedError`, `ModelUnavailableError`, `ParseError`)도 여기에 있다. 공통 모듈은 OpenRouter가 HTTP 200 본문에 `error` 객체를 담아 보내는 경우를 그 코드의 상태로 처리하고, 400(이 모델이 받지 못하는 요청)도 대체 모델 전환 사유로 본다.

## 6. 모델 호출 시 유의점

- 출력이 길어지므로 `max_tokens`는 2000 이상으로 넉넉히 잡는다. 추론 토큰이 포함될 수 있다.
- **429·5xx:** 2초 뒤 한 번만 다시 시도하고, 그래도 실패하면 대체 모델을 차례로 시도한다. 모델이 없거나(404) 사용 불가(403·410)여도 다음 모델로 넘어간다. 401(키 문제)은 넘어가지 않는다.
- **대체 모델 목록:** 2026-10-22에 같은 레시피 요청(재료 5개, 3개 요청, 추론 끔)으로 무료 텍스트 모델을 시험해 정했다. 모델당 1회라 편차가 있다.

  | 모델 | 시간 | 결과 |
  |---|---|---|
  | `nemotron-3.5-lightning` | 10~16초 | 가장 빠르지만 불안정: 한 번은 JSON 파싱 실패, 한 번은 3개를 요청했는데 1개만 줌 |
  | `nemotron-3-ultra-550b` (기본) | 20초 | 3개 모두 우리 재료 사용, 가장 안정적 |
  | `poolside/laguna-s-2.1` | 25초 | 3개, 일부 어색한 조합 |
  | `nemotron-3.5-super-vl` | 35초 | 3개 |
  | `recursive/flint` | — | 추론을 끌 수 없어 400 → 제외 |
  | `nemotron-3-super-120b` | — | 이 계정에서 404 → 제외 |
  | `laguna-xs`, `xing4.0` | — | 429 → 제외 |

  기본 모델은 처음에 속도를 보고 `lightning`으로 정했으나, 형식 오류와 개수 부족으로 재시도·추가 요청이 붙어 호출(하루 한도)이 늘 수 있고 제목에 없는 재료를 지어내는 일이 있어서, 안정성을 우선해 **`ultra`를 기본으로 바꿨다**. `lightning`은 대체 1순위다. 두 모델의 크기 차이는 약 18배(활성 파라미터 3B 대 55B)이고 컨텍스트·최대 출력(65,536토큰)·가격(무료)은 같다. 무료 한도는 토큰이 아니라 호출 횟수로 센다.
  기대 시간은 정상이면 20~30초(시험 1회 기준), 요청이 몰려 한 번 재시도하고 대체 모델까지 가는 최악의 경우는 50~60초다.
- 모델 가용성은 하루 만에도 바뀐다. 같은 날 이미지 쪽에서는 기본 모델이던 `minimax/minimax-m3.1-flash:free`의 무료 기간이 끝나 404가 나서 `nemotron-3.5-super-vl`로 교체했다. 모델 전환·결과 문구는 "사용 불가"와 "혼잡"을 구분해 안내한다.
- **하루 한도:** 무료 모델은 계정당 호출 횟수에 하루 한도가 있다(크레딧 10달러 미만 계정은 하루 50회, 분당 20회, UTC 기준 초기화). 429가 일시 혼잡인지 한도 소진인지 응답으로 구분해 안내 문구를 다르게 한다(구현됨, 구분 방법과 안내 문구는 PRD 1단계 6장). 한도 소진이면 "잠시 후 다시"가 틀린 안내이므로 초기화 시각(한국 시각)을 알려 주고, 대체 모델도 같은 한도를 쓰므로 시도하지 않는다. 모든 모델이 사용 불가(서비스 종료 등)인 경우와 형식 오류인 경우도 각각 맞는 안내를 쓴다.
- 이 모델의 한국어 품질은 사전 테스트(간단한 질의응답)로만 확인했다. 레시피 품질은 구현 시 샘플 10건으로 직접 평가한다.
- 프롬프트에는 "입력 재료에 없는 재료는 `have: false`로 표시", "안전하지 않은 조리법(익히지 않은 닭고기 등) 금지"를 명시한다.

## 7. 비기능 요구사항

- **성능:** 정상 응답 기준 레시피 3개 생성은 30초 이내를 목표로 한다. 무료 모델이라 보장하지 않는다.
- **안전:** 재료 목록, 조건 입력은 길이를 제한(예: 재료 50개, 항목당 30자)하고 프롬프트에 넣을 때 사용자 입력을 지시문과 구분해서 전달한다. 사용자 입력 속 지시문이 모델 동작을 바꾸지 못하게 한다.
- **남용 방지:** 세션당 분당 요청 수를 제한한다. 방문자 IP를 안정적으로 얻기 어려워 IP 대신 세션 기준이며 완전한 방어는 아니다.
- **고지:** 알레르기 정보는 모델이 틀릴 수 있으므로 화면에 "알레르기는 직접 확인하세요"를 항상 표시한다.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 재료 목록이 비어 있음 | 요청 거부, 1단계로 돌아가도록 안내 |
| 모델 응답 파싱 실패(빈 `choices` 포함) | 1회 재요청 후 실패하면 실패했다고 표시 |
| 제한 조건 때문에 남은 레시피가 0개 | 조건을 완화하도록 안내 |
| 429 / 타임아웃 | 재시도, 대체 모델 전환 후에도 실패하면 "요청이 몰려 있습니다" 안내 |
| 하루 무료 한도 소진 | 한도 횟수와 초기화 시각(한국 시각)을 안내하고, 재시도·대체 모델은 시도하지 않는다. 첫 요청에서 소진되면 오류, 두 번째 요청 중 소진되면 이미 받은 레시피를 보여 주고 이유를 경고로 알린다 |
| 모든 모델 사용 불가(404 등) | "AI 모델을 모두 사용할 수 없어요… 관리자에게 알려 주세요" (기다려도 풀리지 않을 수 있음) |

## 9. 수용 기준

- [ ] 1단계에서 확정한 재료로 레시피 3개가 생성된다.
- [ ] 각 레시피에 재료, 조리 단계, 시간, 부족한 재료가 표시된다.
- [ ] 레시피가 한국어로 나온다.
- [ ] 요리 종류(한식·양식·중식·일식), 난이도(초급·중급·고급), 조리 시간(15분 이내·30분 이내·30분 이상)을 고를 수 있고, 고른 조건에 맞는 레시피만 결과에 나온다.
- [ ] 조리 시간 선택지에 "60분 이내"가 없고 "30분 이상"이 있다.
- [ ] 알레르기로 지정한 재료가 포함된 레시피는 결과에 나오지 않는다.
- [ ] 보유하지 않은 재료가 `have: true`로 표시되지 않는다.
- [ ] 응답이 깨졌을 때 앱이 죽지 않고, 이전 결과가 남지 않은 채 실패했다고 표시된다.
- [ ] 429 상황에서 재시도와 대체 모델 전환이 진행 화면에 보인다.
- [ ] 브라우저에서 API 키가 보이지 않는다.

## 10. 구현 결과 (2026-10-22)

- **구현됨:** 조건 입력(인원수, 최대 시간, 알레르기, 식단 제한, 추가 재료 정책, 개수), 진행 단계 표시(요청, 재시도, 대체 모델 전환, 제외, 완료), 레시피 카드·상세·제외 목록, "다시 생성", 실패 시 이전 결과 제거와 실패 표시, 알레르기 고지.
- **화면 흐름:** 1단계 확정 목록 아래에 같은 페이지로 이어 붙였다. 생성이 끝나면 `st.rerun()`으로 화면을 다시 그려 단추 이름("다시 생성")과 결과를 한 번에 갱신하고, 진행 기록은 접힌 영역에 남긴다. 재료를 다시 인식하거나 다시 확정하면 이전 레시피를 지운다.
- **모델 출력은 믿지 않는다:** 화면에 쓰는 모델 글자는 마크다운·링크·수식으로 해석되지 않도록 이스케이프한다(`[클릭](http://…)` 같은 글이 링크가 되지 않는다).
- **진행 기록(2026-10-24 개선):** 요청마다 응답 상태와 걸린 시간, 마지막 줄에 총 소요 시간이 남는다. 형식 오류로 같은 모델에 다시 요청하거나 대체 모델로 넘어갈 때는 원인과 응답 앞부분이 함께 적힌다. 모델이 준 글자는 화면에 쓰기 전에 이스케이프한다.
- **검증:** 단위·화면 테스트(모델 호출은 가짜 응답)가 통과한다. 실제 모델로 2회 시험했다. 기본 조건은 17초에 3개, 알레르기 "우유" 조건은 36초에 3개(형식 오류 1회 재요청, 2개 제외, 모자란 2개를 다시 요청)였고, 우유가 든 레시피는 하나도 나오지 않았다.
- **알려진 한계:** 기본 모델이 가끔 한국어 사이에 영어 단어를 섞거나 오타를 낸다("scrambling하듯", "어느간"). 이름 비교는 단순 규칙이라 드물게 같은 재료를 다르다고 보거나 그 반대일 수 있다. 계량 단위는 모델이 준 그대로 보여 준다. 프로필 기본값 연동은 3단계에서 한다.

## 11. 미결 사항

- 레시피 품질 평가 기준(예: 조리 가능성, 재료 일치율)을 누가 어떻게 볼 것인가?
- 계량 단위(g, 컵, 큰술)를 표준화할 것인가?
- "다시 생성" 시 이전에 나온 레시피를 제외하는 기능이 필요한가?
- 화면 흐름: 지금은 한 페이지에 이어 붙였다. 직접 써 보고 마법사(단계별 화면)나 여러 페이지(`st.navigation`)가 필요한지 정한다.
- 한국어 외 글자가 섞인 레시피를 자동으로 걸러 낼 것인가?
- `ultra`의 실제 응답 시간·성공률은 시험 1~2회뿐이다. 쓰면서 더 모으고, 너무 느리면 `lightning`을 기본으로 되돌릴지 정한다.
