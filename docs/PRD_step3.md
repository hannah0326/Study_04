# PRD 3단계 — 사용자 프로필과 레시피 저장

> 전체 흐름: [1단계 식재료 인식](PRD_step1.md) → [2단계 레시피 생성](PRD_step2.md) → **3단계 프로필·레시피 저장**

## 1. 목적

사용자 프로필을 만들고, 마음에 드는 레시피를 저장해 다시 볼 수 있게 한다. 프로필에 저장된 식단 제한과 알레르기는 2단계 레시피 생성의 기본 조건이 된다.

## 2. 범위

**포함**
- 프로필 생성·선택·수정·삭제
- 프로필별 식단 제한·알레르기·기본 인원수 저장
- 레시피 저장, 목록 조회, 상세 보기, 삭제
- 저장 시 원본 재료 정보와 메모 보관

**제외**
- 소셜 로그인, 이메일 인증, 비밀번호 찾기
- 프로필 간 레시피 공유, 즐겨찾기 정렬 추천
- 냉장고 사진 자체의 저장(개인정보 보호)

## 3. 사용자 스토리

1. 사용자로서 내 프로필을 만들어 취향과 알레르기를 한 번만 입력하고 싶다.
2. 사용자로서 마음에 든 레시피를 저장하고 나중에 다시 보고 싶다.
3. 사용자로서 저장한 레시피에 메모를 남기고 싶다.
4. 사용자로서 필요 없어진 레시피와 내 프로필을 삭제하고 싶다.

## 4. 기술 구성

| 항목 | 결정 |
|---|---|
| 저장소 | SQLite (파일 DB, 서버와 같은 프로젝트에 둠) |
| 접근 | 서버 엔드포인트를 통해서만 접근 |
| 프로필 구분 | 아래 5.1의 방식 중 결정 필요(미결 사항 참고) |

DB 파일(`*.db`)은 사용자 데이터이므로 `.gitignore`에 추가한다.

## 5. 기능 요구사항

### 5.1 프로필
- 프로필 필드: 이름(필수, 중복 불가), 기본 인원수, 식단 제한 목록, 알레르기 목록, 생성 일시
- 프로필 인증 방식은 학습용 앱의 범위를 고려해 **프로필 선택 + 4자리 PIN**을 기본안으로 한다.
  - PIN은 평문으로 저장하지 않고 솔트를 포함한 해시로 저장한다.
  - 인증 성공 시 서버가 서명된 세션 쿠키(HttpOnly, SameSite=Lax)를 발급한다.
- 프로필 삭제 시 그 프로필의 저장 레시피도 함께 삭제한다. 삭제 전 확인 창을 띄운다.

### 5.2 레시피 저장
- 2단계 레시피 상세 화면의 "저장" 버튼으로 현재 선택한 프로필에 저장한다.
- 저장 항목: 레시피 전체(제목, 요약, 인원, 시간, 난이도, 재료, 부족 재료, 단계), 저장 당시 보유 재료 목록, 메모, 저장 일시
- 같은 프로필에서 제목과 재료 구성이 같은 레시피를 중복 저장하려 하면 "이미 저장됨"으로 안내한다.
- 프로필당 저장 개수 상한은 200개이다.

### 5.3 저장한 레시피 보기
- 목록: 최신순, 제목 검색, 시간·난이도 필터
- 상세: 저장 시점의 내용 그대로 표시, 메모 수정, 삭제
- 저장한 레시피는 AI를 다시 호출하지 않고 DB 내용만 보여 준다.

### 5.4 2단계 연동
- 프로필이 선택되어 있으면 레시피 생성 조건의 식단 제한·알레르기·인원수를 프로필 값으로 미리 채운다.
- 프로필이 없어도 1·2단계는 그대로 쓸 수 있다. (저장 시점에만 프로필을 요구)

### 5.5 서버 엔드포인트

| 메서드·경로 | 설명 |
|---|---|
| `POST /api/profiles` | 프로필 생성 |
| `GET /api/profiles` | 프로필 이름 목록(PIN 정보 제외) |
| `POST /api/profiles/{id}/login` | PIN 확인 후 세션 발급 |
| `PATCH /api/profiles/{id}` | 프로필 수정(본인만) |
| `DELETE /api/profiles/{id}` | 프로필과 레시피 삭제(본인만) |
| `POST /api/recipes` | 레시피 저장 |
| `GET /api/recipes` | 내 저장 목록(검색·필터) |
| `GET /api/recipes/{id}` | 상세 |
| `PATCH /api/recipes/{id}` | 메모 수정 |
| `DELETE /api/recipes/{id}` | 삭제 |

모든 레시피·프로필 변경 엔드포인트는 세션의 프로필과 대상 소유자가 일치하는지 서버에서 확인한다. 다른 프로필의 데이터는 조회·수정할 수 없다.

## 7. 비기능 요구사항

- **보안:** SQL은 반드시 파라미터 바인딩을 쓴다. 화면 출력 시 레시피 텍스트는 이스케이프한다(모델 출력도 신뢰하지 않는다). PIN 시도는 5회 실패 시 일정 시간 잠근다.
- **개인정보:** 사진 원본은 저장하지 않는다. 저장되는 개인 정보는 프로필 이름, 식단·알레르기, 레시피뿐이다.
- **백업:** DB는 파일 하나이므로 복사만으로 백업된다. OneDrive 동기화 폴더에 두면 DB 파일이 깨질 수 있으므로 프로젝트를 OneDrive 밖에 두거나 DB 경로를 밖으로 지정한다.
- **API 키:** 3단계에서도 키는 서버만 사용하며 DB·로그에 남기지 않는다.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 프로필 이름 중복 | 다른 이름을 쓰도록 안내 |
| PIN 불일치 | 일반적인 "정보가 올바르지 않습니다" 문구, 실패 횟수 누적 |
| 세션 없음·만료 상태로 저장 시도 | 프로필 선택 화면으로 이동 후 저장 재시도 |
| 저장 개수 상한 초과 | 오래된 레시피 삭제 안내 |
| DB 오류 | 일반 오류 문구, 서버 로그에 상세 기록 |

## 9. 수용 기준

- [ ] 프로필을 만들고 PIN으로 로그인할 수 있다.
- [ ] 프로필의 알레르기가 2단계 생성 조건에 자동으로 채워진다.
- [ ] 레시피를 저장하면 서버를 재시작해도 목록에 남아 있다.
- [ ] 저장한 레시피의 메모를 수정하고 삭제할 수 있다.
- [ ] 다른 프로필의 레시피를 URL이나 ID로 직접 조회하려 하면 거부된다.
- [ ] DB에서 PIN이 평문으로 보이지 않는다.
- [ ] 프로필 삭제 시 해당 프로필의 레시피도 사라진다.
- [ ] `*.db`가 git에 추적되지 않는다.

## 10. 미결 사항

- 인증 방식: PIN을 쓸지, 인증 없이 "프로필 선택"만 할지(개인 PC 전용이면 단순화 가능)
- 여러 사람이 같은 서버를 쓰는 배포를 가정하는가, 개인 로컬 실행만 가정하는가?
- 저장한 레시피의 "다시 생성" 또는 변형(재료 대체) 기능이 필요한가?
- 프로필 데이터 내보내기(JSON) 기능이 필요한가?
