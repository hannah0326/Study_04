# PRD 3단계 — 사용자 프로필과 레시피 저장

> 전체 흐름: [1단계 식재료 인식](PRD_step1.md) → [2단계 레시피 생성](PRD_step2.md) → **3단계 프로필·레시피 저장**

## 1. 목적

사용자가 로그인해 프로필을 만들고, 마음에 드는 레시피를 저장해 다시 볼 수 있게 한다. 프로필에 저장된 식단 제한과 알레르기는 2단계 레시피 생성의 기본 조건이 된다. 이 단계는 AI 모델을 호출하지 않는다.

## 2. 범위

**포함**
- 로그인(구글 로그인, 선택적으로 이메일·비밀번호)과 로그아웃
- 프로필 생성·수정·삭제 (식단 제한, 알레르기, 기본 인원수)
- 레시피 저장, 목록 조회, 상세 보기, 메모 수정, 삭제
- 저장 시 저장 당시 보유 재료와 메모 보관

**제외**
- 이메일 인증 메일 발송, 비밀번호 찾기
- 사용자 간 레시피 공유, 추천 정렬
- 냉장고 사진 자체의 저장(개인정보 보호)

## 3. 사용자 스토리

1. 사용자로서 구글 계정으로 간편하게 로그인하고 싶다.
2. 사용자로서 식단 제한과 알레르기를 프로필에 한 번만 입력하고 싶다.
3. 사용자로서 마음에 든 레시피를 저장하고 나중에 다시 보고 싶다.
4. 사용자로서 저장한 레시피에 메모를 남기고, 필요 없어진 것은 삭제하고 싶다.
5. 사용자로서 앱이 잠들었다 깨어나거나 재배포되어도 저장한 내용이 남아 있기를 원한다.

## 4. 기술 구성

| 항목 | 결정 |
|---|---|
| 앱 | Python + Streamlit (1·2단계와 같은 앱) |
| 배포 | Streamlit Community Cloud (무료) |
| 저장소 | **Supabase(Postgres)** — 앱 서버 밖의 외부 DB |
| DB 접속 | Postgres 연결 문자열(`DATABASE_URL`)로 서버에서만 접속 (psycopg2 등) |
| 로그인 | Streamlit 내장 `st.login`(OIDC)으로 구글 로그인. 이메일·비밀번호 로그인은 선택 |

**왜 로컬 SQLite를 쓰지 않는가:** Streamlit Community Cloud는 접속이 없으면 앱을 재우고, 재부팅·재배포하면 서버 디스크가 처음 상태로 돌아간다. 파일 DB(SQLite)에 저장하면 프로필과 레시피가 사라질 수 있다. 그래서 처음부터 외부 DB를 쓴다.

**비밀 값 관리**

| 값 | 로컬 | 배포(Streamlit Secrets) |
|---|---|---|
| `OPENROUTER_API_KEY` | `.env` | 최상위 키로 입력 |
| `DATABASE_URL` | `.env` | 최상위 키로 입력 |
| 구글 로그인 값(`redirect_uri`, `cookie_secret`, `client_id`, `client_secret`, `server_metadata_url`) | `.streamlit/secrets.toml`의 `[auth]` 블록 | `[auth]` 블록으로 입력 |

- Secrets는 `[auth]` 아래에 적은 줄이 모두 `[auth]`에 속한다. 따라서 `OPENROUTER_API_KEY`, `DATABASE_URL`을 먼저 적고 `[auth]` 블록을 맨 뒤에 둔다.
- 연결 문자열, DB 비밀번호, 클라이언트 보안 비밀은 채팅·로그·화면·저장소에 남기지 않는다. `.streamlit/secrets.toml`은 git에서 제외한다.

## 5. 기능 요구사항

### 5.1 로그인과 프로필
- 구글 로그인 버튼으로 로그인하면, 구글이 보낸 이메일로 사용자 행을 찾고 없으면 만든다. 비밀번호는 구글만 확인하고 앱은 저장하지 않는다.
- (선택) 이메일·비밀번호 로그인을 함께 둘 경우, 비밀번호는 솔트를 포함한 해시로만 저장한다. 구글로 가입한 사용자는 비밀번호 칸이 비어 있으며, 이메일·비밀번호 폼으로는 로그인할 수 없다.
- 프로필 필드: 표시 이름, 기본 인원수, 식단 제한 목록, 알레르기 목록. (요리 종류·난이도·조리 시간 같은 선호 조건은 2단계 화면을 직접 써 본 뒤 추가 여부를 정한다)
- 로그아웃하면 재료·레시피 등 진행 중이던 화면 상태를 모두 비운다. (이전 사용자의 화면이 남지 않게)
- 계정 삭제 시 그 사용자의 저장 레시피도 함께 삭제한다. 삭제 전 확인을 받는다.

### 5.2 레시피 저장
- 2단계 레시피 상세 화면의 "저장" 버튼으로 로그인한 사용자 계정에 저장한다. 로그인하지 않았다면 로그인 안내 후 저장을 이어 가게 한다.
- 저장 항목: 레시피 전체(제목, 요약, 인원, 시간, 난이도, 재료, 부족 재료, 단계), 저장 당시 보유 재료 목록, 메모, 저장 일시
- 같은 사용자가 제목과 재료 구성이 같은 레시피를 다시 저장하려 하면 "이미 저장됨"으로 안내한다.
- 사용자당 저장 개수 상한은 200개이다.

### 5.3 저장한 레시피 보기
- 목록: 최신순, 제목 검색, 시간·난이도 필터
- 상세: 저장 시점의 내용 그대로 표시, 메모 수정, 삭제
- 저장한 레시피는 AI를 다시 호출하지 않고 DB 내용만 보여 준다.

### 5.4 2단계 연동
- 로그인되어 있으면 레시피 생성 조건의 식단 제한·알레르기·인원수를 프로필 값으로 미리 채우되, 사용자가 바꿀 수 있다.
- 로그인하지 않아도 1·2단계는 그대로 쓸 수 있다. (저장 시점에만 로그인을 요구)

### 5.5 모듈 구성

Streamlit 앱에는 별도 HTTP 엔드포인트가 없으므로, 아래 모듈이 DB와 인증을 맡는다.

| 위치 | 설명 |
|---|---|
| `src/db.py` | Supabase 연결과 프로필·레시피 조회·저장·삭제. 모든 SQL은 파라미터 바인딩을 쓴다 |
| `src/auth.py` | 구글 로그인 상태 확인, 사용자 행 조회·생성, (선택) 비밀번호 검증 |
| `src/app.py` | 로그인 버튼, 프로필 화면, 저장 버튼, 저장한 레시피 화면 |

## 7. 비기능 요구사항

- **권한:** 로그인한 사용자의 id를 서버에서 확인하고, 레시피 조회·수정·삭제는 항상 `user_id`가 일치하는 행만 대상으로 한다. 다른 사용자의 데이터는 ID를 알아도 접근할 수 없다.
- **Supabase 공개 API 차단:** 앱은 Postgres에 직접 접속하므로 Supabase의 행 수준 보안(RLS)은 앱의 권한 검사를 대신해 주지 않는다. 다만 Supabase가 자동으로 여는 데이터 API로 외부에서 테이블을 읽지 못하도록 두 테이블에 RLS를 켜고 공개용 정책은 만들지 않는다.
- **연결 끊김 복구:** 앱이 잠들었다 깨어나면 풀에 남은 DB 연결이 이미 끊겨 있을 수 있다. 연결 시간 초과를 짧게(예: 8초) 두고, 꺼낸 연결에 확인 쿼리를 보내 죽었으면 연결 풀을 새로 만든다.
- **연결 방식:** 짧게 연결했다 끊는 서버리스 성격이므로 Supabase의 Transaction pooler(포트 6543)를 기본으로 한다. IPv4만 되는 환경에서 직접 연결(포트 5432)은 막힐 수 있다.
- **보안 점검:** 출력 시 레시피 텍스트를 신뢰하지 않는다(모델 출력도 이스케이프). 로그인 실패 시 일반적인 문구만 보여 계정 존재 여부를 알리지 않는다. 오류 화면에 DB 연결 문자열·쿼리·스택 정보를 노출하지 않는다.
- **개인정보:** 사진 원본은 저장하지 않는다. 저장되는 개인 정보는 이메일, 표시 이름, 식단·알레르기, 레시피뿐이다.
- **구글 로그인 설정:** 구글 클라우드 콘솔에서 동의 화면(외부)과 웹 애플리케이션 OAuth 클라이언트를 만들고, 승인된 리디렉션 URI에 `http://localhost:8501/oauth2callback`과 배포 주소의 `/oauth2callback`을 모두 넣는다. 외부 동의 화면은 테스트 모드에서 등록한 테스트 사용자만 로그인할 수 있으므로 본인 계정을 테스트 사용자로 추가한다.

## 8. 오류 처리

| 상황 | 동작 |
|---|---|
| 로그인 설정이 비어 있음 | 앱이 멈추지 않고 "로그인을 사용할 수 없습니다"를 보여 준다 |
| 로그인하지 않은 채 저장 시도 | 로그인 안내 후 저장을 이어 가게 한다 |
| 저장 개수 상한 초과 | 오래된 레시피 삭제를 안내한다 |
| DB 연결 끊김·시간 초과 | 연결을 새로 만들어 1회 재시도하고, 그래도 실패하면 일반 오류 문구를 보여 주고 서버 로그에 상세를 남긴다 |
| 이메일·비밀번호 불일치(선택 기능) | "정보가 올바르지 않습니다"만 보여 준다 |

## 9. 수용 기준

- [ ] 구글 계정으로 로그인·로그아웃할 수 있고, 로그아웃하면 이전 화면 상태가 남지 않는다.
- [ ] 프로필의 알레르기와 인원수가 2단계 생성 조건에 자동으로 채워지고 수정할 수 있다.
- [ ] 레시피를 저장한 뒤 앱을 재부팅(Reboot app)해도 목록에 남아 있다.
- [ ] 저장한 레시피의 메모를 수정하고 삭제할 수 있다.
- [ ] 다른 사용자의 레시피를 ID로 조회·수정·삭제하려 하면 거부된다.
- [ ] 계정을 삭제하면 해당 사용자의 레시피도 사라진다.
- [ ] 비밀번호를 쓰는 경우 DB에서 평문으로 보이지 않는다.
- [ ] Supabase 데이터 API로 `users`, `saved_recipes`를 읽으려 하면 거부된다.
- [ ] 연결 문자열과 클라이언트 보안 비밀이 저장소·화면·로그 어디에도 없다.

## 10. 미결 사항

- 이메일·비밀번호 로그인을 함께 둘 것인가, 구글 로그인만 둘 것인가? (비밀번호를 다루면 해시·실패 횟수 제한 등 보안 부담이 늘어난다)
- 로컬 개발에서 `DATABASE_URL`이 없을 때 임시로 SQLite를 쓰게 할 것인가, Supabase를 필수로 할 것인가?
- 프로필에 요리 종류·난이도·조리 시간 같은 선호 조건을 저장할 것인가?
- 저장한 레시피의 변형(재료 대체)이나 데이터 내보내기(JSON)가 필요한가?
